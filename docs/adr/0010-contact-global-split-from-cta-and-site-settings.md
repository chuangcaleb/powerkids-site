# 0010. Split a `contact` global out of `cta` and `site-settings`

**Status:** accepted
**Date:** 2026-09-20

## Context

The blue "Contact" footer band and enquiry-form admin config had their fields spread across two globals for unrelated reasons:

- `cta.contact` held only the band's heading/lead copy. `cta`'s own docblock scoped it deliberately to public copy for the two footer sections (enquiry, contact) — contact facts were kept out on purpose.
- `site-settings` held the facts (`email`, `phones`, `openingHours`, `openingDays`, `socials`) plus unrelated fields (`enquiryNotificationEmail`, `defaultShareImage`, `locations`, `locationsMapPoster`).
- [footer-contact.tsx](../../src/components/footer/footer-contact/footer-contact.tsx) renders the Contact band by reading both globals and joining them at render time — the two-global split served no reader, only the admin's edit screen.

Two fields don't fit a naive "just merge everything Contact-shaped" read:

- `email`, `phones`, `socials` are also read by [layout.tsx](<../../src/app/(site)/layout.tsx>) for sitewide JSON-LD structured data — a consumer with nothing to do with the footer band. Moving them still works (the new global is just as reachable), but their identity is "sitewide contactable facts," not "Contact-section-only facts."
- `locations` / `locationsMapPoster` render in a separate "Find us" section, never in the Contact band. Despite the name, they aren't contact-copy consumers and were excluded from the move.
- `enquiryNotificationEmail` is never rendered publicly — it's server-only ops config read in the enquiry-notification hook. It doesn't belong with public Contact copy/facts at all.

## Decision

Create a new `contact` global: `header` (moved from `cta.contact`) plus `email`, `phones`, `openingHours`, `openingDays`, `socials` (moved from `site-settings`). `cta.contact` is retired.

`enquiryNotificationEmail` moves instead into `cta.enquiry`, alongside that section's copy — grouped by "what an admin touches when editing the Enquiry section," not by public/private-field semantics. Its `admin.description` must say plainly it's not rendered copy, since everything else in that group is.

`locations` / `locationsMapPoster` stay on `site-settings` — they render in an unrelated section, name notwithstanding.

Schema migration is Payload-autogenerated from the config diff; existing singleton values are re-entered by hand in the admin panel post-deploy rather than hand-written into a data migration — cost of typing back a handful of scalar/array values once is lower than migration code for a one-time move.

## Consequences

`site-settings` keeps `defaultShareImage`, `locations`, `locationsMapPoster`, `enquiryNotificationEmail` is removed from it — none of these are contact-shaped, the name stays accurate for what's left. `cta` keeps `footerSticker` and `enquiry` (now including the notification address) — its scope loosens slightly from "public copy only" to "what an admin edits for the Enquiry section," a narrow, named exception, not a reversal. A `get-contact.ts` getter joins the other global getters (`get-cta.ts`, `get-site-settings.ts`); `footer-contact.tsx` and `layout.tsx`'s JSON-LD both move to it, replacing the two-global read.

## Alternatives considered

- **Nest contact facts as `cta.contact.{email, phones, ...}` instead of a standalone global.** Rejected — `cta`'s scope is public copy for two footer bands; folding in sitewide facts also consumed by JSON-LD re-blurs the line 0003's sibling docs try to keep clean, for no gain over a standalone global.
- **Fold `locations`/`locationsMapPoster` into the new `contact` global too, since the name suggests it.** Rejected — they render in an unrelated "Find us" section; grouping by name instead of by actual renderer would recreate the same colocation-by-vibes problem this ADR fixes.
- **Leave `enquiryNotificationEmail` on `site-settings`.** Rejected — it has nothing to do with site-wide brand facts; grouping by "what an admin edits together" put it in `cta.enquiry` instead, next to the section's other Enquiry-admin fields.
- **Hand-write a data migration to carry over existing singleton values.** Rejected — one-time move of a handful of scalar/array values on a singleton row; manual re-entry post-deploy is cheaper than migration code to write and test.
